== Summary ==================================================================

Every run gets group 3 code 1 (model id c2a0d2), code 2 (BLE address
4451d3805163) and code 9 (firmware "1.0.0.3") unprompted, right after the
channel opens — same as every other Fast Pair device in PROTOCOL.md. Group 4
code 1 (payload 033c) is unexplained; it is not battery (wrong group/code)
and this probe does not attempt to decode it further.

**No run, across 12s, 30s and 60s, ever produced a group 3 code 3 battery
frame** — the shape PROTOCOL.md documents for every other Fast Pair device
here, single-byte for a one-battery set like this one. This probe's own
`08 11 00 00` (Fast Pair Hearable Control "get ANC state", sent 1.5s after
connect) also got no reply, matching the JBL device's documented absence of
that same message group.

The widget nonetheless shows a battery figure (100%, confirmed live via
`omarchy-shell omaphones status` and `bluetoothctl info`'s own `Battery
Percentage: 0x64 (100)` line) — this is BlueZ's own native reading, not
anything from this channel. `Service.qml`'s own comment says this fallback
exists: "the headset's own figure where there is one battery, otherwise the
lowest earbud, or BlueZ's rounded single figure when the Message Stream has
said nothing." This device is the "said nothing" case.
